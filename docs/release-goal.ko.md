## 해결할 문제와 데모

환기 설비가 명령을 수락한 뒤에도 풍량이 시설의 운영 목표에 미달할 수 있다. 이때 운영 담당자는 문제가 해결됐는지, 정비 담당자는 같은 설비의 어떤 부분을 먼저 확인할지 알아야 한다. 고용노동부의 학교 급식실 환기 점검은 성능 개선이 실제 필요한 사례다. 보고서의 현장 조사와 데모의 가상 입력을 각각 표시한다. 시설 간 장비 연동 문제는 제품에서 시험할 가설이다. [고용노동부 점검 자료](https://www.moel.go.kr/news/enews/report/enewsView.do?news_seq=18528)

**목표는 시설 관리자가 에이전트와 대화해 구역과 가상 상황을 설정하고, 실제 oneM2M 현장 운영 앱과 선택형 MEC 정비 앱이 한 사건에서 서로 다른 결정을 내리는 과정을 재현할 수 있는 오픈소스 릴리스다.** 프로필은 허용 조치와 목표값, 앱 구성은 실행 위치와 권한, 시나리오는 가상 입력과 기대 결과를 담는다. 지원 센서·단위·동작 유형 안에서 새 ID와 구역을 설정으로 추가한다. 새 장치 유형을 위한 어댑터 확장 경로도 제공한다.

첫 장면에서 운영자는 가상 댐퍼에 100%를 요청하고 장비 ACK를 받는다. 후속 가상 풍량이 360 m³/h, 해당 프로필의 목표가 900 m³/h이면 사건은 열린 상태다. 정비 앱은 해당 설비의 개도 센서에 추가 관측을 요청한다. 독립적인 가상 센서가 최신 35%를 보고하면 **이미 열려 있던 작업지시서**의 점검 순서가 ‘구동부·개도 피드백 우선 점검’으로 바뀐다. 결함의 원인은 현장 점검에서 확인한다. 두 번째 시설에서는 사용자가 대화로 지정한 구역의 오래된 관측으로 조치를 요청해 장비 명령 생성이 거부되는 장면을 보여준다.

## 같은 사건을 처리하는 계층

이번에 MEC에 올릴 프로젝트는 독립 배포 가능한 **정비 패키지 한 개**다. 같은 이미지에서 정비 앱과 서비스 연동기를 시설별로 각각 실행한다. 기존 현장 운영 앱이 장치 명령을 맡고, MEC 정비 앱은 작업지시서의 점검 순서를 담당한다. 실제로 별도 제공자의 센서가 필요할 때 MEC를 선택하는 조건, 각 앱의 권한과 검증 시나리오는 [애플리케이션별 배포·서비스 계약](mec-application-contract.ko.md)에 고정했다.

| 주체와 위치 | 소유하는 결정 | 검증 지점 |
| --- | --- | --- |
| 가상 장치 AE, 시설 단말 | 원본 관측·ACK 발행 | 측정 시각·단위·출처, 장치 ID, 명령 ID |
| 운영 AE와 MN-CSE, 현장 | 운영 AE가 사건·허용 명령·후속 회복을 판정. MN-CSE가 자원·구독·권한을 제공 | Mca 원본 CIN, 후속 관측, 역할별 ACP, 작업 앱 중단 중에도 운영 지속 |
| 정비 AE와 서비스 연동 어댑터, MEC 호스트 | 정비 AE가 자기 시설의 사건을 구독하고 MN-CSE에 센서 요청을 발행. 어댑터가 해당 요청을 실제 MEC 서비스 호출로 변환하고 응답을 CSE에 기록. 정비 AE는 이를 읽고 작업지시서를 갱신 | CSE 요청 → 실제 서비스 발견·설정·소비 → CSE 응답 재조회. 서로 다른 권한, 동일 사건·작업 ID |
| 중앙 IN-CSE와 조회 앱 | Mcc로 등록한 현장의 공유 상태를 종합 | 공유된 자원과 마지막 갱신 시각을 표시. 중앙 단절과 담당 CSE 전환의 시험은 각각 기록 |
| Codex·독립 LLM 실행기·대시보드 | 같은 서비스 계약에서 시나리오 작성·가상 실행·결과 확인 | 권한은 서버가 판단. 시나리오 작성자는 실행 결과를 지정할 수 없음 |

**Option C**를 채택한다. TR-0080의 C는 같은 엣지 노드에 플랫폼을 두는 구성이다. 수업 TR-0086 §5.2·5.4의 `dep-opt-c`에서는 MN-CSE가 MEC 앱으로 구동되고 openSoom 정비 AE는 별도 앱 인스턴스로 등록된다. 위의 서비스 어댑터는 openSoom의 요청을 중계하는 논리 역할이다. TR-0086의 Option B용 별도 MEC-IPE 설치를 C의 전제조건으로 추가할 필요는 없다. GCP VM은 Sandbox의 기반이며 화면에는 실제 플랫폼 실행, 모의 엣지 호스트, 가상 장치를 구별한다. [TR-0080 §5.1](https://specifications.onem2m.org/tr/tr-0080/latest/5.1/) · [ESTIMED 교육 자료](https://estimed.etsi.org/dev_material/)

여섯 Rubric 심사팀과 별도로 GPT-6.2-Sol Max **Idea Model 검토자**를 둔다. R0에서 문제·경계·근거, R2/R3에서 현장 단독·MEC·동일 근거의 로컬 대조와 재사용, R4/R5에서 화면·발표의 주장을 검토한다. 메인 에이전트가 제안에 대한 채택·수정·보류 이유를 남긴다. [검토 계약](review/review-charter.json)

R1·R2·R3은 계약을 정한 뒤 병행할 수 있다. 이번 테스트의 무결성은 같은 시설·자산·구역·사건·명령·작업 ID와 정확한 원본 CIN을 따라 검증한다. 계정 없는 데모에는 fixture가 쓰인 위치를 표시한다. 프로필별 임계값과 가상 운영 결과를 사람의 건강 개선 효과로 해석하지 않는다.

R1과 R3의 새 신원은 인증된 연결의 자격증명에 시설별 origin을 바인딩한다. R2는 두 어댑터에서 기존 TS-0023 PM2.5 자원을 발견·조회하는 회귀 시험을 유지한다. 시험은 운영 중인 사건과 분리된 가상 시설 데이터에서 한다.

## 제한 시간과 배포 예산

- **11월 19일**에는 R0 사양 확인과 가장 작은 MEC 왕복, R1 현장/정비 통합, R2 새 구역 가상 실행을 우선한다. 같은 날 릴리스 후보와 가용한 화면을 동결해 720p로 녹화한다. **20일**에는 검토·수정·GitHub·기사/영상 전달을 우선한다. **22일 일요일**까지 필요한 슬라이드 파일도 이번 Goal의 산출물에 포함한다. 평가는 **23–25일**이다. 정확한 제출 마감 시각은 공지에서 확인되지 않았다. [공식 일정](https://onem2m-hackathon.io/schedule.asp)
- 사용자가 승인한 테스트용 **GCP VM 한 대, 월 약 US$30 규모**로 진행한다. 작업공간의 비공개 `.runtime/goal-cloud-scope.json`에서 승인 프로젝트를 읽고 각 명령에 명시한다. 재실행 전 동일 VM을 조회·재사용한다. 부팅 디스크·주소·트래픽까지 포함해 해당 리전 월 환산 추정액을 확인하고 기록한다. 기본 운영은 캡처 후 VM을 중지하고 필요한 리허설에만 다시 켜는 것이다. 잔여 디스크·주소 비용과 재시작 방법을 남긴다. 1대에서의 논리 호스트와 독립 물리 호스트 수를 구분한다. [GCP 가격](https://cloud.google.com/products/compute/pricing)
- ETSI의 STF_685 설치 가이드는 Kubernetes 마스터 1대와 선택형 워커 구성을 지원한다. 이 경로는 한 대에서 시험할 수 있지만 승인 비용대에서 실제 서비스가 함께 기동하는지는 실측해야 한다. TR-0086 Annex B에 맞춰 고정 주소와 OAuth 콜백도 점검한다. [ETSI 배포 가이드](https://labs.etsi.org/rep/mec/etsi-mec-sandbox/-/blob/STF_685/deploy/pyinfra/README.md)
- Sandbox 전체가 예산·메모리·인증 조건을 충족하지 못하면 원인과 필요한 최소 조건을 기록한다. 동일 예산에 맞는 다른 구성이나 사용할 권한이 있는 실제 MEC 환경에서 검증을 이어간다. 로컬 앱 통합, 데모, 랜딩·발표·GitHub는 계속 진행한다. 대체 가능한 실제 비위치 MEC 서비스는 운영자가 보는 결정이 달라지고 원래 기준을 충족할 때만 채택한다. 로컬 축소판을 배포해도 R3는 실제 플랫폼 왕복까지 열린다.
- 설치 중인 최종 시연과 다른 격리 포트·DB로 작업한다. 실행기 모델 비용은 기존 공유 예산에서 차감하며 재시도·작업자 간 누계를 유지한다. 기존 승인의 공개 가능한 가상 시설 데이터만 전송한다. 실장비 조작, 다른 프로젝트 자원, 외부 게시 권한은 이 배포 범위 밖이다.

## Expert 심사와 제출 인계

모든 항목의 목표 등급은 Expert다. 이전 릴리스에서 충족한 항목도 이번 변경으로 영향받으면 같은 후보 버전에서 재심사한다. **13번**은 자체 시설 토폴로지와 적격 MEC 호스트 간 실제 배치 결정을 플랫폼 기록으로 확인한다. **16번**은 서로 다른 기능 서비스 둘 이상을 oneM2M에서 발견·설정·소비하고 양방향 동작을 확인한다. 예컨대 실지원되는 MEC 033으로 새 시설의 연결 대상을 실제 변경하고, 046으로 그 시설의 작업을 갱신한다. 단순 디렉터리 조회는 서비스 두 개의 증명이 되지 않는다. 두 Expert 검증을 한 대 비용 내에서 적극 추진한다. 서비스 목록·적격 호스트·실험 결과와 미충족 요건을 심사표에 각각 적는다. R3의 제품 왕복이 통과해도 한 서비스 또는 한 배치만 확인되면 해당 Expert 항목은 열린 상태다.

14번은 ESTIMED VM과 실제 연합학습, 15번은 네트워크·MEC·oneM2M 위치 연계로 동작이 바뀌는 사례가 필요하다. 데이터 현지성이나 이동 자산의 필요가 확인되면 해당 팀이 범위를 재검토한다. 6번의 실게시 기사 역링크, 8번의 실제 공개 기술 논의, 9번의 실제 인터뷰는 당사자의 외부 행위에 의존한다. 제품 릴리스 준비와 실제 17개 Expert 판정을 별도로 집계한다. [심사 기준 대조표](review/release-goal-review.ko.md)

발표는 영어 10–15분, 데모 영상 재생 포함, 구현 설명 약 1분 이내로 리허설한다. 영문 슬라이드는 문제 근거 → 관리자의 결정 → 한 사건의 실제 시연 → 다른 시설에서 재사용 → 왜 oneM2M/MEC인지 → 직접 실행 순서로 구성한다. 공개 기사에 GitHub와 재생 가능한 데모 URL을 넣고 Discord에는 공개 기사 URL을 제출하는 것이 주최 측 절차다. Drive 슬라이드 업로드와 시간표 C·D, G–AJ의 X 및 주최 측 PICK 확인을 인계표에 둔다. 현재 자동으로 게시할 대상은 사용자가 지정한 GitHub다. [제출 인계](submission/handoff.md)
