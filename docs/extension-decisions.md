# Conditional extension decisions

The table below records first-release decisions. The subsequent release ran a project-specific topology on the ETSI Sandbox. The platform installed the MN and maintenance app on two selected logical edges, and a scoped oneM2M request commissioned a provider through MEC 033 before a MEC 046 lookup updated an open work order. Decision date: 18 November 2026, Asia/Seoul. These are product-scope decisions submitted to independent review, not official rubric N/A decisions or scores. All 17 criteria remain visible. A deferred capability is absent from release claims.

| Extension | Decision and product reason | Simpler alternative / available environment | Reopen and verify when |
| --- | --- | --- | --- |
| Advanced SDT mapping (criterion 11) | Adopt PM2.5 airQualitySensor FCNT because another consumer can recognize a standard quantity across vendors | Custom canonical CIN remains for full precision and unmapped quantities; actual ACME supports cod:aiQSr | Validate pinned types/units, native discovery and actual app reads for both adapters; record independent review |
| Serving-CSE handover (12) | Adopt for planned maintenance of the facility CSE while an incident or command is pending. Two failed availability probes switch the application to B | Two independent ACME CSEs on one host. The central-outage experiment covers loss of the upstream connection and leaves the serving CSE unchanged | [Repeat the maintenance transfer](handover.md), inspect restored context, source fencing, command deduplication and measured service gap in the [actual run](../evidence/runtime/handover/acceptance.json) |
| MEC deployment (13) | Defer after access investigation. No project-specific authenticated host or deployment permission is available | ESTIMED landing page responds; MEC platform connection failed in this session; local processes remain reproducible | A permitted ESTIMED/MEC host, image deployment right and registration endpoint are available; deploy and retrieve actual hosting logs |
| Federated learning (14) | Defer. No real multi-site dataset or demonstrated learning/data-locality need exists | Configured diagnostic rules are interpretable and sufficient for the simulated cases; no ESTIMED VM access is available | A measurable cross-site learning task and ESTIMED VM path exist; test multiple clients, aggregation, dynamic participation and failures |
| Network/MEC geolocation (15) | Defer. Fixed ventilation zones do not currently change behavior based on mobile location | Facility/zone identity already supplies the required scope; a static map would not prove location integration | Moving equipment or responders require genuine service events that alter placement, policy or handover |
| MEC services (16) | Defer. Platform-discovery/onboarding is a plausible service use, but no authenticated service instance is available and MEC033 availability was not established | oneM2M discovery covers the present facility equipment requirement | A supported non-location service has a product use, oneM2M/IPE resource mapping and observable application behavior; direct side-by-side API calls are insufficient |

The feasibility record is `evidence/stage0/mec-feasibility.json`. Public URLs alone do not grant access or custom-image hosting. The supplied TR-0086 deployment example informs what to test once access exists; its presence does not establish our deployment. The failed connection is session-specific and is not evidence of a global platform outage.

The filmed central outage and subsequent serving-CSE maintenance transfer have separate execution records. Process migration, orchestration and MEC service consumption remain open. This scope retains architectural depth through native distributed CSE operations, explicit authority, expiry/replay handling and verified local control, each tied to a concrete operating need.
