# openSoom 한국어 해설과 발표 대본

openSoom은 **장비의 작동 여부와 시설의 공기 상태를 함께 확인하고, 조치 이후의 결과까지 추적하는 오픈소스 운영 도구**입니다. 급식실은 출발 사례이며, 제품의 단위는 시설·구역·장비·관측·프로필·사건입니다. 식품 생산 시설과 다른 환기 필요 공간에 같은 코어를 적용하되, 목표값과 허용 조치는 시설별로 설정합니다.

이 문서는 발표자의 이해를 돕는 해설입니다. 영어 공개 피칭은 [단일 페이지](../pitch/index.html), 검증 기록은 [현재 자체 평가](hackathon/current-assessment.md), 심사 질문은 [영어 Q&A](submission/technical-qa.md)에 있습니다. HTML은 파일을 직접 더블클릭하기보다 `pitch/README.md`의 로컬 서버로 여세요. Three.js 모듈은 같은 폴더의 고정 버전을 사용합니다.

## 1. 어떤 문제를 풀고 있나요?

2026년 10월 11일 연합뉴스 보도에 인용된 평가에서는 환기시설을 개선한 급식실 301곳 중 17.9%가 부적정 판정을 받았습니다. 이 숫자로 제시할 수 있는 문제는 **설치·작동 확인만으로 목표 성능을 보장하기 어렵다는 것**입니다. 제조사 간 데이터 연동 문제가 원인이었다거나 openSoom이 질병을 줄였다고 해석하면 안 됩니다. [보도 원문](https://www.yna.co.kr/view/AKR20261010032900004)

구체적인 가상 시나리오는 이렇습니다. 조리 구역의 팬 상태는 `ON`인데 배기량은 해당 시설의 설정 목표보다 낮습니다. 시스템은 이를 사건으로 기록합니다. 권한이 있는 운영자가 조치를 요청하면 장비의 응답을 기다리고, 그 뒤의 새 관측 두 개로 결과를 확인합니다. 팬에 명령을 보냈다는 이유만으로 사건을 닫지 않습니다.

PM2.5·CO₂는 참고 관측이며, 그것만으로 국소배기 포집 성능이나 건강 보호를 판정하지 않습니다. 데모의 배기량·기준값·장치 응답은 가상 입력입니다. 실제 시설에 사용하려면 적절한 센서, 장비 어댑터, 현장 검증과 시설별 제어 정책이 필요합니다.

## 2. 구조를 다섯 부분으로 읽으세요

| 부분 | 하는 일 | 필요한 이유 |
| --- | --- | --- |
| 장비 어댑터 | 제조사 데이터의 이름·단위·시각을 공통 관측으로 변환 | 제조사를 바꿀 때 진단 로직까지 다시 만들지 않기 위해 |
| oneM2M CSE | 자원 저장, 발견, 구독 알림, 그룹 조회, 접근 권한, 선택적 자원 공유 | 여러 장비와 여러 앱이 같은 서비스 계층을 사용하기 위해 |
| openSoom 운영 서비스 | 프로필, 사건, 명령, ACK, 회복 판정, 실행 기록 | 시설의 운영 규칙과 지속되는 상태를 관리하기 위해 |
| MCP와 AI | 도구를 통해 설치 안내·상태 확인·진단·허용 조치를 수행 | 사용자가 내부 API를 직접 다루지 않고 작업하기 위해 |
| 대시보드 | 구역 상태와 실행 과정을 읽기 쉽게 표시 | AI의 설명과 실제 기록이 일치하는지 사람이 확인하기 위해 |

**CSE**는 oneM2M의 공통 서비스 기능이 실행되는 서버입니다. **AE**는 CSE를 사용하는 애플리케이션의 식별 단위입니다. 관측과 명령은 컨테이너에 저장되는 **CIN**, 알림은 **SUB**, 그룹은 **GRP**, 권한은 **ACP**로 구현합니다. 이 이름을 모두 외울 필요는 없습니다. “장비 앱·진단 앱·운영 앱이 공통 자원을 서로 다른 권한으로 사용한다”가 핵심입니다.

### 전체 아키텍처를 화면에서 읽는 순서

`The shared layer` 아래 **Every layer has a job**에서 전체 구조를 크게 볼 수 있습니다. 두 설치 방식은 별도 시연 구성이며, 두 화면을 하나의 배포로 합쳐 설명하지 않습니다.

- **One installation:** 하나의 현장 서비스와 보안 CSE 안에 두 예시 시설의 자원이 있습니다. 34개 선택 항목은 장비·리소스 묶음·논리 모듈을 포함하므로 34개 프로세스라는 뜻이 아닙니다.
- **Two facilities:** 현장 API 2개, MN-CSE 2개, 중앙 IN-CSE 1개를 별도 로컬 프로세스로 실행한 구성을 46개 항목으로 펼칩니다. 중앙 자원 공유와 명시적 재처리를 설명할 때 사용합니다.
- **Follow a path:** `Observe & diagnose`는 관측과 진단, `Command → ACK → result`는 명령·응답·후속 관측, `Share & reconcile`은 선택적 공유와 현장 검사를 강조합니다. `Agent tool boundary`에서는 모델의 요청과 서버의 권한 검사를 구분합니다.
- **구성요소 선택:** 모델, 경로의 번호 버튼 또는 `Component index`에서 항목을 선택하면 한국어 설명·실행 경계·자원 경로·소스 근거가 아래에 표시됩니다. `Pause paths`로 움직임을 멈출 수 있고, 모바일에서는 같은 구성요소를 읽기 쉬운 그룹 목록으로 제공합니다.

가령 `Device acknowledgements`를 선택한 뒤 “ACK는 장비 응답이고, 회복은 그 뒤의 서로 다른 정상 관측 두 개로 확인합니다”라고 설명하세요. 중앙 연결의 점선 에이전트 경로는 공통 서비스 인터페이스를 뜻합니다. 실제 에이전트 실행 증거는 단일 설치에서 확보했으며, 분산 에이전트 세션을 별도로 검증했다고 말하지 않습니다. [구성요소와 소스 대응표](../evidence/pitch/architecture-source-map.json), [브라우저 확인 범위](../evidence/pitch/architecture-browser-qa.json)

## 3. 왜 oneM2M인가요?

장비 하나와 화면 하나라면 단순한 API나 MQTT만으로도 구현할 수 있습니다. openSoom은 서로 다른 제조사, 시설 프로필, 진단·운영 역할이 같은 증거를 재사용하는 상황을 대상으로 합니다. 이때 발견, 알림, 그룹 조회, 접근 제어와 원격 자원 공유를 애플리케이션마다 따로 만들지 않는 데 oneM2M의 가치가 있습니다.

단일 설치 보안 프로필에서는 장비 어댑터가 oneM2M의 **네이티브 MQTT/TLS 바인딩**으로 관측과 ACK를 CSE에 보냅니다. 운영 서비스는 **HTTPS**로 CSE 자원을 읽고 명령을 씁니다. 일반 MQTT 메시지를 중간에서 HTTP로 바꾸는 것만으로 네이티브 바인딩이라고 부르지 않습니다. 로컬 API·콜백은 HTTP, MCP는 stdio이며, 별도 분산 프로필의 CSE 간 Mcc도 HTTP입니다. 전체 경로가 TLS라고 설명하지 않습니다.

데이터의 뜻도 맞춰야 합니다. 예를 들어 제조사 B의 `0.012 mg/m³`를 공통 관측 `12 µg/m³`로 변환합니다. PM2.5는 고정한 oneM2M SDT 모델의 정수 필드로도 투영하고, 원본 정밀도는 별도 관측에 유지합니다. CO₂의 ppm을 질량 농도 필드에 그대로 넣는 식의 억지 매핑은 하지 않았습니다. [매핑 설명](standard-model.md)

## 4. AI는 어디까지 맡나요?

Codex 플러그인은 설정과 운영 절차를 안내하고 MCP 도구에 연결합니다. 별도 LLM API 실행기는 실제 모델이 같은 도구를 선택해 작업하게 합니다. 플러그인 등록, MCP 연결, 서비스 준비, 실제 모델 추론은 각각 별도의 검증입니다. 정확한 호스트 검증 범위와 최신 결과는 [에이전트 증거 인덱스](../evidence/agent/index.json)를 기준으로 설명하세요.

AI는 시스템 관리자 권한을 스스로 만들지 못합니다. 서비스가 역할·시설·프로필·관측 시각·허용 조치를 검사합니다. 설치 프로필의 활성화는 별도의 관리자 역할로 처리됩니다. 실행 상태는 대화 기록이 아니라 서비스에 저장됩니다.

발표에서는 다음 세 문장을 구분하면 됩니다.

1. **명령 저장:** CSE가 요청을 받았습니다.
2. **장비 ACK:** 가상 장치가 적용했다고 응답했습니다.
3. **회복 확인:** 그 뒤의 서로 다른 최신 정상 관측 두 개가 확인됐습니다.

실제 모델 시험에서 오래된 증거로 제어를 요청한 사례는 서버가 명령 저장 전에 차단했습니다. 이를 “모델이 스스로 위험을 알아서 거부했다”고 바꾸어 말하지 마세요. 이것은 AI와 별개로 집행되는 서비스 검사가 필요한 이유를 보여줍니다.

## 5. 복수 시설과 MEC는 무슨 차이인가요?

현장마다 MN-CSE를 두고 중앙 IN-CSE에 필요한 자원을 공유하는 구조를 실제 로컬 프로세스로 실행했습니다. 중앙을 중단한 동안에도 시험한 현장 관측→명령→ACK→회복 흐름은 이어졌습니다. 재연결 후에는 만료된 중앙 지시와 중복 실행을 검사했습니다.

이는 **중앙 연결 장애 중 현장 연속성**입니다. 애플리케이션이 다른 CSE로 이동하는 handover, VM 이동, 실제 ETSI MEC 배포를 뜻하지 않습니다. MEC는 네트워크 엣지에서 애플리케이션과 서비스를 제공하는 프레임워크이며, 로컬 서버나 Docker 컨테이너라는 이유만으로 MEC가 되지 않습니다.

이번 릴리스에서는 접근 환경과 제품 필요성을 검토한 뒤 MEC 배포·서비스, CSE handover, 연합학습, 위치 서비스를 보류했습니다. 심사 기준에서 자동으로 제외되거나 점수를 받는다는 뜻은 아닙니다. [확장 결정과 재개 조건](extension-decisions.md)

## 7. 심사 질문에 답하는 짧은 기준

- **무엇이 실제인가요?** CSE 자원과 프로토콜, 서비스 상태, MCP 호출, 기록된 실제 모델 API 실행입니다. 물리 센서·장비·시설 값은 가상입니다.
- **건강 효과를 입증했나요?** 아닙니다. 이 PoC는 관측부터 결과 확인까지의 운영 흐름과 상호운용을 검증했습니다.
- **보안이 완성됐나요?** 역할·시설·ACP 거절과 특정 TLS 구간을 검증했습니다. loopback 개발 환경의 신뢰 경계와 외부 배포 시 필요한 인증은 문서에 구분했습니다. CSE 식별 헤더만으로 강한 사용자 인증을 주장하지 않습니다.
- **왜 복잡한가요?** 제조사 형식, 앱별 권한, 현장/중앙 장애, 결과 검증이라는 서로 다른 문제를 각 구성요소가 담당합니다. 시설 하나를 시작할 때 전체 분산 구성을 강제하지 않습니다.
