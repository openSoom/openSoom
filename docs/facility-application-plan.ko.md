# openSoom 시설별 앱 구성 및 오늘 밤 개발 계획

11월 19일 후속 결정과 확정 완료 기준은 [릴리스 목표](release-goal.ko.md)에 있다. 아래 회의 기록에서 제안한 정비 서비스 경로는 후속 검토를 반영해 MN-CSE에 서비스 요청을 발행하고 응답을 재조회하는 구조로 구체화했다.

2026년 11월 18일 KST · 회의 피드백 검토와 구현 계획

## 회의 피드백과 제품 방향

회의 메모의 우선 질문은 **oneM2M–MEC를 연동할지, A–D 중 어디에 MN-CSE를 배치할지, 각 계층에서 어느 앱을 실행할지**다. 데이터의 출처와 판정 규칙, 단절 또는 전환 때 어떤 데이터와 작업이 이어지는지도 배치에 맞춰 설명해야 한다. **시설 종류에 종속되지 않는 앱을 제공하고 사용자가 에이전트와 대화해 새 시나리오를 만들 수 있게 하는 것**은 사용자가 추가한 제품 방향이다.

기존 프로젝트는 현장 MN-CSE와 중앙 IN-CSE를 실제로 연결했다. 당시 접근 확인 이후 MEC 배포와 서비스 연동은 보류로 기록됐다. 자체 Sandbox 설치 경로를 별도 실증으로 추진하는 작업이 빠져 있어 Rubric 13·16은 아직 실행 근거가 없다. 로컬 CSE 단절·전환 근거는 Rubric 12의 범위다. [MEC 접근 기록](../evidence/stage0/mec-feasibility.json) · [Rubric 근거표](hackathon/rubric-baseline.json)

## 결정

**첫 MEC 배치는 GCP 자체 ETSI Sandbox의 Option C다.** 선택한 엣지 호스트에서 MN-CSE와 MEC 정비 앱을 독립 인스턴스로 실행한다. 현장 운영 앱은 Mca로 MN-CSE를 사용해 관측·명령·ACK를 기록하고 결과를 판정한다. MEC 정비 앱은 전용 AE로 같은 MN-CSE의 사건을 읽고 해당 설비에 대한 서비스 요청을 MN-CSE에 쓴다. 연동 어댑터가 이를 Mp1 서비스 호출로 매핑하고 결과를 MN-CSE에 기록하면 정비 앱이 응답을 읽어 점검 순서를 갱신한다. 중앙 IN-CSE는 Mcc를 통해 현장의 공유 상태를 조회한다. 현장 게이트웨이와 MEC를 독립 노드로 배치할 필요가 생기면 같은 앱 계약을 Option B에 적용할 수 있다. [oneM2M 배포 옵션](https://specifications.onem2m.org/tr/tr-0080/latest/5.1/) · [ESTIMED 실습 자료](https://estimed.etsi.org/dev_material/)

openSoom은 환기가 필요한 시설이 공통 운영 기반에서 앱과 시나리오를 선택할 수 있게 한다. **시설 프로필**은 관측 기준과 허용 조치, **앱 구성**은 어느 앱에 어떤 자원과 권한을 줄지, **시나리오**는 어떤 장면을 어떤 가상 입력으로 재현할지 정한다. 식품 생산과 학습 공간은 이 계약을 재사용하는 사례다.

## 앱 구성과 권한

| 예시 구성 | 장비·현장 계층 | 선택형 정비 앱 | 중앙 |
| --- | --- | --- | --- |
| 학습 공간 | 장치 어댑터, 현장 운영, 대시보드 | 기본 운영만 구성 | 별도로 설정한 경우 공유 상태 조회 |
| 식품 생산 | 동일 장치·운영 계약과 시설별 프로필 | 독립 정비 프로세스가 같은 사건의 작업을 관리. 로컬 ACME에서 먼저 확인하고 검증된 호스트에서 MEC 서비스 연결 | 별도로 설정한 경우 공유 상태 조회 |

시설 ID마다 활성 앱, 해당 AE가 구독할 자원, 기록할 자원과 배포 위치를 명시한다. 현장 설정과 호스트 연결·인증 값은 역할이 다르며, 시설에서 앱을 선택하는 행위는 장치 제어 권한을 부여하지 않는다.

- **운영 경로**에는 기존 대시보드 API와 Codex MCP 도구를 사용한다. 현장 운영 서비스가 원본 관측, 사건, 명령, ACK와 회복 상태를 확정한다.
- **정비 경로**에는 시설별 전용 AE와 작업지시서·보조 증거 컨테이너를 둔다. 기본 정비 AE의 공용 `commands` 쓰기 권한은 현재 API 차원의 조치 구분에 사용된다. 새 앱의 권한은 별도 ACP로 구성한다. CSE가 타 시설 조회와 장치 명령 생성에 `4103`을 반환하는지 확인한다. [기본 ACP](../src/opensoom/core.py#L110) · [독립 실험의 권한 응답](../evidence/runtime/multiapp-revalidation/no_recovery/result.json)
- **사건 연결**은 시설·구역·사건 ID와 원본 관측 CIN을 공통으로 사용한다. 현장 코어가 사건 발생과 ACK 후 미회복을 각각 결과 스트림에 발행한다. 발행 대기를 영속 기록하고 재시도는 기존 사건 및 제어 처리에서 분리한다. 정비 앱은 알림 뒤 정확한 CIN을 다시 읽고, 시설·구역·사건에 고정된 한 작업지시서를 생성하거나 갱신한다. 대시보드는 연결된 작업을 읽기 전용으로 표시한다. [현장 판정 코드](../src/opensoom/core.py#L218) · [현재 상태 API](../src/opensoom/core.py#L523)

## 에이전트와 새 시나리오 만들기

현재 시나리오 목록에는 여섯 이름과 설명이 있고, 가상 장치와 종료 판정이 런타임에서 이름별로 분기한다. Codex 설정 도구는 기존 프로필 확인과 관리자 활성화를 지원한다. 대화로 새 시나리오를 작성·저장·실행하는 검증은 새 범위다. [시나리오 목록](../scenarios/scenarios.json) · [현재 실행 분기](../src/opensoom/core.py#L427) · [Codex 설정과 도구](agent-integration.md)

최소 버전의 입력은 `시나리오 ID / 시설 / 구역 / 지원 동작 유형 / 가상 입력값 / 예상 결과`다. 대화에서 에이전트가 지원 센서와 조치 목록을 확인하고 초안을 만든다. 서비스는 구역, 입력 단위와 범위, 허용 유형을 검증한 뒤 가상 실행을 시작한다. 예상 결과는 대조 기준으로 쓰고, 실제 판정은 서비스가 CSE 관측·ACK·결과를 읽어 결정한다. 시설 정책 변경은 기존 관리자 절차를 따른다.

식품 시설의 ACK 후 미회복과 학습 시설의 라운지에서 오래된 관측을 확인하는 시나리오를 같은 실행기로 검증한다. 에이전트로 **새 ID의 시나리오 하나를 작성**하고, 설치 코드나 새 전용 실행기 없이 저장한 설정을 재실행하는 것이 범용성의 첫 증거다. 처음에는 지원된 가상 입력·조치 유형을 조합할 수 있다. 새로운 물리 장치나 동작 유형은 어댑터·검증을 거쳐 추가한다.

## 시연 완료 기준

1. 같은 현장 운영 코어에서 두 시설이 서로 다른 앱 조합으로 시작한다. 사용자가 에이전트와 만든 새 설정을 실제 CSE로 실행하고, 기존 단일 시설의 기본 시나리오도 통과한다.
2. 정비 앱이 구독하는 시설에서 `댐퍼 명령 100% · 장비 ACK · 풍량 360 / 목표 900`이 발생하면 현장 운영은 미해결 상태를 유지한다. 정비 작업은 한 건 열린다.
3. 실제 046 API가 별도 가상 개도 센서의 최신 `35%` 관측을 반환하면, 정비 앱이 **같은 작업에서 구동부·개도 피드백 우선 점검**을 제안한다. 장비 식별자와 관측 시각이 일치할 때 이 분기를 사용한다. 오래된 값이나 응답이 없으면 **추가 근거 미확인**을 남긴다. [ETSI MEC 046](https://www.etsi.org/deliver/etsi_gs/MEC/001_099/046/03.02.01_60/gs_MEC046v030201p.pdf)
4. 사건 발생 전에 정비 앱을 중단해도 현장 기본 운영과 결과 검증은 계속된다. 재시작하면 누락 사건을 CSE에서 자동으로 재조회한다. 이어서 같은 이벤트를 재전달하고 작업 기록 직후 재시작해도 작업지시서는 한 건이다. 타 시설 조회와 장치 명령 생성은 CSE에서 거부된다.
5. 046 또는 자체 플랫폼 왕복이 지연되면 두 시설의 앱 구성과 권한 분리 실증을 시연본으로 확정한다. 기존 담당 CSE 전환은 별도 시험으로, 보류 명령이 있는 상황에서 A를 내리고 B가 같은 명령 ID를 복원하며 가상 적용을 한 번만 수행한 기록을 사용한다. [전환 실험](handover.md)

MEC 배포와 등록은 Rubric 13번, MEC 046에서 받아 oneM2M을 통해 실제 동작에 반영한 기록은 16번의 근거가 된다. 13번 Expert에는 적격 호스트 간 오케스트레이션, 16번 Expert에는 복수 서비스 발견·설정·소비 및 양방향 상호작용을 추가로 검증해야 한다. [루브릭 근거표](hackathon/rubric-baseline.json)
