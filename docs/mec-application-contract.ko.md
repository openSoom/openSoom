# openSoom 운영 앱과 MEC 정비 앱

2026년 11월 19일 통합 실증. 실제 ETSI Sandbox 컨트롤러가 프로젝트의 ACME MN-CSE와 정비 앱을 같은 논리 엣지에 배포했다. 운영자가 한 VM 안의 북쪽·남쪽 호스트를 차례로 선택했고 각 호스트에서 MEC 033으로 외부 가상 센서 제공자를 연결한 뒤 MEC 046 측정 응답으로 기존 작업지시서를 갱신했다. 장비와 측정값은 가상이다. [배포 방법과 경계](../deploy/mec-sandbox/README.md) · [두 호스트의 플랫폼 기록](../evidence/runtime/option-c/index.json) · [로컬 비교](../evidence/runtime/maintenance-release-local.json)

## 해결하려는 현장 판단

2025년 11월 고용노동부는 서울 강서구의 한 학교 급식실을 점검하고 부족한 환기 성능의 개선을 권고했다. 영국 HSE는 국소배기설비를 인수·검증할 때 각 후드의 실제 성능과 운전 조건을 확인하고 풍량·압력 등의 기준값과 측정 결과를 기록하도록 안내한다. 두 자료는 현장에서 설비의 작동 표시와 환기 성능을 각각 확인할 이유를 준다. 개별 시설의 목표값은 운영자가 제공하는 시운전 자료나 프로필에서 가져온다. 현재 예시 수치는 시뮬레이션 값이다. [고용노동부 현장점검](https://www.moel.go.kr/news/enews/report/enewsView.do?news_seq=18528) · [HSE의 국소배기설비 성능 확인](https://www.hse.gov.uk/lev/commissioning.htm)

**운영자는 ‘조치 후 성능이 회복됐는가’, 정비 담당자는 ‘어떤 부위를 먼저 점검할 것인가’를 판단한다.** 일부 설치에서 현장 운영자와 별도 서비스 제공자가 장비를 관리하고, 기계축 위치 같은 추가 센서 관측은 후자가 엣지 센서 공유 서비스로 제공한다는 것이 제품 가설이다. 실제 도입처를 확보했다는 주장은 현장 확인 전까지 보류한다. 동일 품질의 독립 측정이 현장 시스템에 이미 있다면 oneM2M에서 그대로 이용할 수 있다. MEC 구성을 선택하는 이유는 별도로 관리되는 센서에 공통 방식으로 접근하는 데 있다.

## 무엇을 어디에 배포하는가

기본 설치에는 기존 openSoom 운영 서비스와 CSE를 둔다. 확장 설치에는 같은 저장소에서 별도로 빌드·버전 관리하는 **openSoom MEC 정비 패키지**를 추가한다. [정비 패키지](../apps/mec-maintenance/README.md)는 하나의 OCI 이미지에서 아래 두 역할을 독립 프로세스·인스턴스로 실행한다. 이미지, 두 진입점, Sandbox 배포 명세 및 시설별 자원 권한 예제가 이 패키지의 산출물이다. 한쪽을 재시작해도 상대 쪽의 신원과 권한은 유지한다. 특정 시설·실행에서 제어를 담당하는 운영 앱과 활성 MN-CSE는 각각 하나다. 기본 설치와 Option C를 나란히 시험할 때는 같은 코어를 서로 다른 가상 시설 인스턴스·DB·CSE·자격증명으로 기동한다. 한 정비 프로세스 중단 시험과 MN-CSE 또는 VM 장애 시험의 결과를 구별한다.

| 실행 주체 | 역할과 허용된 쓰기 | 배치 및 현재 상태 |
| --- | --- | --- |
| 장치 어댑터와 현장 운영 앱 | 장치는 관측·ACK를 발행한다. 운영 앱만 시설 정책에 따라 장치 명령을 내리고 후속 관측으로 사건의 회복을 확정한다. 새 결과 스트림에 판정과 원본 관측 ID를 남긴다. | 기존 oneM2M 운영 서비스. 실제 CSE 결과를 대시보드에 표시한다. [현장 실행](../evidence/runtime/maintenance-release-local.json) |
| MN-CSE와 IN-CSE | MN-CSE는 현장의 자원·구독·권한을 제공한다. 중앙 IN-CSE는 Mcc로 공유된 현장 자원을 조회 경로에 제공한다. | 두 현장 MN-CSE와 중앙 IN-CSE의 실행 기록이 있다. Option C에서는 Sandbox가 배포한 프로젝트 ACME MN-CSE 인스턴스에 운영·정비 AE가 Mca로 연결된다. [다중 CSE 실행](../evidence/runtime/product-multisite-continuity.json) |
| **엣지 정비 워커** | 자기 시설 사건을 읽어 작업 한 건을 연다. 필요 시 MN-CSE에 센서 조회 요청을 작성한다. 응답을 다시 읽어 **작업지시서와 점검 순서**를 갱신한다. | [정비 워커](../src/opensoom/maintenance_worker.py)는 시설별 전용 AE로 CIN을 재조회하고 대상 작업을 갱신한다. |
| **MEC 서비스 연동기** | 허용된 서비스 요청을 읽어 플랫폼에서 적합한 서비스를 발견한다. MEC API를 호출하고 원본 측정 시각·센서 ID·단위·출처가 붙은 응답을 MN-CSE에 쓴다. | 같은 새 패키지의 연동 진입점, 별도 시설별 AE. MEC 서비스 자격증명은 이 인스턴스에만 둔다. 정비 앱과 연동기 모두 장치 명령 권한을 갖지 않는다. |
| **정비사용 웹 앱** | 특정 작업지시서 판본의 근거와 첫 점검을 읽고, 일정·현장 점검·전문가 요청을 기록한다. 해당 판본에 연결된 상태만 운영자에게 돌아가며 메모는 정비사 전용이다. | 사람을 위한 독립 웹 서비스와 시설별 전용 계정. 현장 운영 콘솔과 별도 포트에서 실행한다. [브라우저 검증](../evidence/application/technician-browser.json) · [실행 방법](../apps/technician/README.md) |
| Codex 플러그인·독립 LLM 실행기 | 시설의 지원 기능을 확인하고 관리자에게 쓸 수 있는 조합을 안내한다. 가상 시나리오를 검증·저장·재현하고 서버에서 결과를 읽는다. 설정 변경은 기존 시설별 권한을 따른다. | 실제 Codex와 독립 모델이 각각 다른 이름의 라운지 시나리오를 작성했다. [원본 CIN과 재실행](../evidence/agent/scenario-authoring/README.md) |

Option C는 두 플랫폼을 같은 엣지 노드에 배치하는 선택이다. 여기서 **openSoom이 제공하는 소프트웨어는 정비 패키지**이고 **플랫폼에서 소비하는 기능은 ETSI 표준 서비스**다. Sandbox 컨트롤러가 설치한 ACME MN-CSE와 정비 앱은 별개 인스턴스다. 연동기는 재배치 중에도 시설별 고정 엔드포인트를 유지한다. TR-0086의 내부 통신·콜백 경로를 사용한다. 자기 시설에 연결하려는 장치·운영 앱에 유효한 인증 및 접근 경로가 있어야 한다. [oneM2M TR-0080 배포 옵션](https://specifications.onem2m.org/tr/tr-0080/latest/5.1/) · [ESTIMED 개발 자료](https://estimed.etsi.org/dev_material/)

자체 클라우드에서도 사람용 웹 서비스와 MEC 워커를 독립적으로 운영했다. 남쪽 논리 호스트의 작업지시서 판본을 정비사 웹 API로 열어 일정을 저장하자 운영자가 같은 접수 번호를 조회했다. 같은 요청을 재전송해도 접수는 한 건이고, 처리 전후 장비 명령은 여섯 건으로 같았다. 기술자 웹 서비스는 일반 Kubernetes Deployment로 배치한 별도 비공개 Pod에서 실행했다. [클라우드 실행의 원본 요청과 응답](../evidence/runtime/option-c/technician-handoff.json)

## 어떤 MEC 서비스가 제품에서 무슨 일을 하는가

| 사용 서비스 | 구체적 동작과 검증 |
| --- | --- |
| **MEC 046 Sensor-sharing · 독립 측정** | 관리자의 시설 요청을 처리한 연동기가 실제 센서 데이터 구독을 등록하고 연결 확인 통지를 받는다. 구독 ID를 다시 읽는다. 정비 작업에 쓰는 가상 축 개도는 별도의 센서 조회에서 받아 원본 시각·단위·설비가 맞을 때 MN-CSE에 기록한다. [구성·측정 실행](../evidence/runtime/option-c/commissioned-sensor-roundtrip.json) · [ETSI GS MEC 046](https://www.etsi.org/deliver/etsi_gs/MEC/001_099/046/03.02.01_60/gs_MEC046v030201p.pdf) |
| **MEC 033 IoT API · 제공자 연결** | 승인된 관리자 요청 CIN을 받아 011을 통해 033을 발견한다. 지정된 제공자가 없으면 등록하고 활성화된 등록 내용을 다시 읽는다. 연결되지 않은 동안 열려 있던 센서 요청은 이후 같은 작업지시서에 결과를 돌려준다. [실제 등록과 측정](../evidence/runtime/mec-provider-commissioning.json) · [ETSI GS MEC 033](https://www.etsi.org/deliver/etsi_gs/MEC/001_099/033/03.01.01_60/gs_MEC033v030101p.pdf) |
| **MEC 011 · 배포 및 서비스 발견 기반** | 실제 배포의 등록·서비스 목록·엔드포인트 증거를 남긴다. 서비스 목록을 읽은 횟수는 046과 033의 실제 기능 사용과 별도 집계한다. |

실증은 프로젝트가 패키징한 ACME와 자체 구성한 headless Sandbox에서 수행했다. 주최 측 기본 콘솔 이미지를 그대로 설치하는 경로는 별도 검증 대상이다. [재현 절차와 플랫폼 경계](../deploy/mec-sandbox/README.md)

## 같은 사건으로 제품 가설을 시험하는 방법

1. 동일 시설 프로필과 가상 입력을 고정한다. 댐퍼 명령 100%, 장비 ACK, 후속 풍량 360 m³/h, 이 시설의 목표 900 m³/h를 준비한다. 제어기 자체 보고·센서 원본·명령값은 화면에서 별도로 식별한다.
2. 정비 앱을 켠 상태에서 보조 관측 없이 실행하면 운영 사건은 미해결, 작업은 일반 현장 점검 한 건이다. 연동기를 켠 경우 정비 AE의 서비스 요청 CIN → 연동기의 실제 046 조회/통지 → 결과 CIN → 정비 AE의 재조회가 연결돼야 한다. 앱 간 연계에는 시설·구역·자산·사건·작업·요청 ID를 사용한다.
3. 올바른 기계축 위치 센서의 35%가 해당 명령의 안정화 시간 이후에 측정됐으며 신선도와 단위를 만족하면, 같은 작업의 첫 점검이 ‘구동부·개도 피드백 확인’으로 바뀐다. 운영 사건은 계속 열어 둔다. 같은 센서의 값이 명령과 일치하면 불일치 경고를 해제하고 잔여 풍량 저하를 시설 점검 절차에 넘긴다. 위치값만으로 댐퍼 고장의 원인을 확정할 수 없다.
4. 다른 설비·과거 측정·측정 시각 누락·서비스 단절, 또는 기존 장치 자기보고를 046 값으로 되돌려 보내는 경우에는 새 독립 근거를 채택하지 않는다. 같은 응답을 재전달해도 작업은 한 건이다. 유효한 동일 독립 관측을 로컬 oneM2M 경로로 제공하는 대조 시험에서는 같은 점검 결론이 나와야 한다. 새 MEC 서비스의 가치는 별도 제공자가 운영하는 센서를 기존 제어 코드 변경 없이 연결한 시점에 입증된다.
5. 별도 제공자가 센서를 교체하면 승인된 자산 연결표만 수정해 새 센서로 같은 점검 결과를 얻는지 확인한다. 제어 앱 코드 변경 수와 관리자가 한 설정 단계를 기록한다.
6. 두 시설에서 같은 릴리스와 MCP 도구를 사용한다. 프로필·앱 목록·자산 연결표만 바꾼다. 다른 구역을 대상으로 관리자가 대화로 만든 새 시나리오를 저장하고 재실행한다. 지원하지 않는 센서를 요청하면 필요한 기능이나 어댑터를 알려준다. 시나리오 작성자가 넣은 기대값이 실제 CSE 상태와 다르면 불일치를 기록한다.


두 시설의 사전 정의한 18개 가상 시험에서 같은 원본 관측을 세 판단 규칙에 입력했다. 추가 점검이 필요한 16건 중 ACK만 보는 규칙은 14건, 풍량만 보는 규칙은 2건을 회복으로 닫았다. openSoom은 16건 모두 열어 두었고 실제 회복으로 설계한 두 건은 확인했다. 기계축과 풍량의 점검 순위는 현장 정비의 출발점이다. OSHA 배기설비 점검 지침에도 낮은 풍량을 일으킬 수 있는 여러 원인이 열거돼 있다. [방법과 원본](inspection-benchmark.md) · [OSHA 산업환기 기술 매뉴얼 부록 III:3-4](https://www.osha.gov/otm/section-3-health-hazards/chapter-3)

## Idea Model 검토 결과

설계 검토에서 제기한 문제는 기존 장치의 자기보고를 독립적인 샤프트 측정으로 잘못 해석할 가능성이었다. 통합판에서는 별도 센서의 원본 CIN 또는 별도 제공자 응답으로 두 값을 구별했다. 정비 업무와 제어 권한을 분리했고, 새 시설을 설정으로 추가해 재시작 후 같은 시나리오를 다시 읽었다. 실제 모델의 시나리오 작성과 스크립트로 검증한 시설 설치는 각각 별도의 실행이다. [새 시설과 권한](../evidence/agent/facility-onboarding.json) · [에이전트별 증거](../evidence/agent/scenario-authoring/README.md)

독립 리뷰에서 오염 지표만 높은 경우까지 샤프트 점검을 요청할 수 있음을 발견해 수정했다. 같은 명령을 수락한 뒤 PM2.5·CO₂·팬 이상만 있고 풍량이 목표에 도달한 동안에는 일반 점검을 유지한다. 이후 저풍량을 확인한 경우에만 축 개도를 요청한다. 명령이 바뀌면 이력은 보존하며 새 명령에 해당하는 측정을 기다린다. [동일 사건과 대조 조건](../evidence/runtime/maintenance-command-followup.json)

현장의 고장 원인 적중률, 외부 제공자가 있는 시설의 도입 비용, 비개발자 단독 설치 시간은 실제 시설·관리자와 검증할 과제다. 현재 내부 판정은 가상 장비를 사용한 오픈소스 제품 시연에 대한 것이다. [17개 심사 및 독립 검토](review/release-assessment.ko.md)
